# 报告契约

> 报告是审核器唯一的产品。它必须让作者**看得懂、信得过、改得动**，而不是让评审团显得专业。

## 1. 报告原则

1. **结论先行**：作者先看总分、等级、一句话判断、最该改的三处，再看细节。
2. **证据可查**：每条问题带正文/素材锚点；没有锚点的判断降为“观察”。
3. **可执行**：修改意见写到“删/移/补/换/压/放”的动作层，不给“加强人物塑造”这类空话。
4. **有取舍**：明确“最该改”和“可以先不改”，避免把二十条问题平铺给作者造成瘫痪。
5. **保留作者**：指出有效选择与亮点，说明哪些地方不要改坏；不把作品改成评审团的风格。
6. **诚实**：材料不足、意见分歧、无法判断，都要写出来；不制造确定感。
7. **不越界**：不代写整章、不直接改文件、不评价作者人品/市场销量/文学史地位。

## 2. 语气与格式

- 默认用中文；用户明确要求英文/其它语言时切换。术语必要时给一句解释。
- 对作者说话，不用“本评审团认为”这类官僚腔；用“这章的问题在于……”“建议……”。
- 批评对事不对人：说“这场戏的转折缺少前置”，不说“作者不会写转折”。
- 不用打分羞辱（“不及格”“垃圾”）；等级是诊断标签，不是判决。
- 短句优先；每段不超过 5 行；问题清单用表格/列表。
- 引用正文用引号 + 锚点；引用不超过定位所需长度。
- 不剧透用户没提供的后续；如果用了后续材料，标注“含后续剧透”。

## 3. 报告结构（必须按顺序）

```markdown
# 正文审核报告：《<章名/编号>》

## 0. 审核摘要
- 总分 / 等级 / 置信度
- 故事设计分（Craft Index）/ 10
- 一句话判断（同时说“逻辑/执行”与“是否好看”）
- 最该先改的三处（按优先级）
- 发布建议（如用户需要）
- 只读声明（一句话，详见 §10）

## 1. 审核范围与依据
- **素材状态**（`已提供 / 用户确认无 / 未确认`）
- 审核对象（正文来源、字数、场景数）
- 素材清单与级别（A/B/C/D）
- 模式（quick/standard/deep）与轮次
- 评审基准：能判什么、不能判什么
- 未纳入材料 / 缺失材料

## 2. 章节速写（事实层）
- 一句话剧情
- 场景表（场景/地点/人物/目标/转折/功能）
- 时间线、视角、关键信息揭示
- 本章承诺与回收

## 3. 分维度评价
### 3.1 人物与矛盾（分数 / 置信度）
### 3.2 故事设计与结构
### 3.3 场景执行与对白
### 3.4 设定与世界逻辑
### 3.5 语言与阅读体验
每节：分数 + 一句理由 + 2–5 条关键 findings + 一条“有效/可保留”

### 3.6 故事设计评分（Craft Scorecard）
| # | 项目 | 分数 1–5 | 证据 | 判断 |
| 1 | 激励事件 | ... |
| 2 | 求索 / 故事脊椎 | ... |
| 3 | 鸿沟 | ... |
| 4 | 场景价值转折 | ... |
| 5 | 序列 / 幕逆转 | ... |
| 6 | 不归点 | ... |
| 7 | 危机 / 高潮 / 结局 | ... |
| 8 | 人物矛盾 | ... |
| 9 | 人物弧 | ... |
| 10 | 类型契约 / 读者体验 | ... |
- 故事设计分（Craft Index）= 10 项平均 × 2
- 与总分的差距 + “是否好看”一句话

## 4. 关键问题清单
| ID | 严重度 | 维度 | 位置 | 问题 | 后果 | 修改方向 |
（P0 在前，P1 次之，P2 最后；OBS 单列）

### P0 · 必须处理
每条：问题 / 为什么成立 / 怎么改（1–3 步）/ 示例（可选，短）/ 代价与风险
### P1 · 建议处理
### P2 · 打磨项
### 不建议改的地方

## 6. 素材一致性核对
- A 级冲突表（如有）
- B/C 级参考提示
- 素材未覆盖的空白
- D 级冲突与待确认项

## 7. 圆桌争议与未决问题
- 分歧点：谁 vs 谁、争什么
- 主持裁定与依据
- 仍不确定什么 / 需要作者补什么
- 魔鬼最有价值的一条挑战及结果

## 8. 亮点与保留项
- 本章真正有效的地方（具体到段落/句子/选择）
- 修改时不要破坏什么

## 9. 评分明细
- 维度分 × 权重
- 原始加权分
- P0 上限及最终分
- 若修掉关键问题，预计可回到多少（区间，不承诺）

## 10. 覆盖范围、限制与只读声明
- 读了什么、没读什么
- 哪些结论受材料不足影响
- 子代理/单线程分演说明
- 未对任何用户提供的输入文件执行写入、重命名、移动或删除
- 报告保存路径（如用户要求保存）
- 运行异常（如有）
```

## 4. 长度建议

| 模式 | 正文字数（不含引用） | 说明 |
|---|---|---|
| quick | 800–1,500 字 | 3–5 条关键问题，不铺开 |
| standard | 2,000–4,000 字 | 完整六维 + P0/P1/P2 |
| deep | 4,000–8,000 字 | 增加逐场分析、争议记录、证据索引 |

长度不是硬指标。宁可 2,500 字说清楚，也不要 8,000 字重复同一件事。

## 5. 问题条目写法

每条必须包含五件事：

1. **位置**：正文锚点（场景 + 引文）；
2. **问题**：具体是什么，不贴空泛标签；
3. **为什么**：机制/因果/规则，让作者能判断你说得对不对；
4. **后果**：读者会怎样、后续会怎样；
5. **怎么改**：动作 + 可选示例 + 代价。

示例（合格）：

> **P1 · 人物 · 场景 3**
> 位置：`[正文·场景3·"他把信折好，放进抽屉最底层"]`
> 问题：林砚决定隐瞒信件，但前文没有任何“他为什么不信任沈鸢”的铺垫。
> 为什么：读者只知道两人是盟友，缺少“隐瞒”的动机；这个动作更像作者需要信息延后，而不是人物选择。
> 后果：读者会觉得人物突然变得防备，后面“沈鸢发现信件”的冲突会像硬拗。
> 改法：① 在场景 2 加一个沈鸢替林砚做决定、越过他边界的细节，让“不信任”有具体来源；② 或把隐瞒改成“他想说但被打断”，保留信息延后，同时不伤害关系逻辑。示例（不是代写）：沈鸢替他答应了差事，他看了她一眼，把话咽回去。代价：场景 2 会多 100–200 字，节奏略慢。

示例（不合格）：

> 人物不够立体，建议加强人物塑造。
> 节奏有点慢，建议加快。
> 设定有问题，建议完善世界观。

不合格原因：没有位置、没有机制、没有可执行动作、无法验证。

## 6. 严重度定义

| 级别 | 定义 | 判断标准 | 处理建议 |
|---|---|---|---|
| **P0 · 阻断** | 不修会影响章节成立/读者信任/后续逻辑 | A 级设定明确冲突；关键因果断裂；人物知识泄漏；核心人物强潜在 OOC 无桥；章节功能不成立 | 必须处理，优先于文采 |
| **P1 · 重要** | 影响阅读体验或后续承接，但章节仍成立 | 动机不足；节奏失衡；场景目标不清；对白无行动；信息倾倒；承诺未处理；关系跳跃 | 建议处理，可分批 |
| **P2 · 打磨** | 局部优化，不影响理解 | 语言重复；句式单调；感官细节不足；比喻不准；段落节奏 | 有余力再改 |
| **OBS · 观察** | 可能是风格选择，证据不足以判错 | 作者可能有意为之；取决于后续；类型惯例 | 只提示，不要求改 |

严重度不是“我觉得多严重”，而是“后果有多硬”。P0 必须能说清“不修会怎样坏”。

## 7. 修改方案写法

### 7.1 动作词表

- **删**：删掉某句/某段/某场，说明删后损失什么、如何补。
- **移**：把信息/场景/揭示移到更合适的位置，说明为什么。
- **补**：补一个动作、细节、过渡、动机桥，说明补多少、补在哪。
- **换**：换视角/换表达/换冲突方式，说明替代方案。
- **压**：压缩解释/重复/描写，说明压到多少。
- **放**：放慢/展开关键 beat，说明展开什么。

### 7.2 每个方案给取舍

- 这个改法解决什么；
- 会带来什么新问题/成本；
- 有没有更便宜的替代；
- 是否与作者意图/文风冲突。

### 7.3 示例的边界

- 可以给 1–2 句示例，帮助作者理解动作；必须标注“示例，不是代写”。
- 不给整段/整场重写，除非用户明确要求“示范改写”；即使如此，也只给局部，并说明这不是唯一解。
- 示例要贴合作者现有文风，不要趁机展示评审团的文采。

## 8. 当问题很少 / 没有问题

- 不要为了显得认真而硬凑问题。可以写“本章未发现 P0/P1；以下为可选打磨项”。
- 如果章节确实优秀，明确说优秀在哪，给高分；不要用“但是”稀释。
- 如果只发现 1–2 个小问题，报告可以短；不必凑满六维长文。
- “没有发现问题”不等于“没有审”：要说明审了什么、覆盖到什么程度。

## 9. 当材料冲突 / 不足

- **素材状态未确认**：写“用户未提供设定/人物卡，且未确认是否存在；以下判断仅按文本内自洽，置信度低”。**不要写“无素材”**；只有用户明确说“没有/只看正文”，才能写“用户确认无外部素材”。
- **A 级冲突**：单列“一致性冲突表”，写清两边原文、影响、让作者选。
- **B 级差异**：写“与参考材料不同，但不构成错误；如果作者想保留旧设定，可忽略”。
- **C 级期待**：写“按目标平台/读者，这类写法可能……”，不写成硬规则。
- **D 级冲突**：写“素材本身存在两个版本，本报告分别标注影响；建议作者确认以哪版为准”。
- **缺失材料**：写“未提供人物卡，人物一致性仅按文本内自洽判断；置信度中”。

## 10. 只读声明（必须出现）

报告末尾固定包含：

```text
只读声明：本次审核仅读取上述材料，未对任何用户提供的输入文件执行写入、重命名、移动或删除。
报告直接输出在对话中。/ 报告已新建于：<路径>（用户明确要求保存）。
```

如果运行中出现异常（子代理失败、材料读取失败、权限不足），在声明前加“运行异常”小节，不要隐瞒。

## 11. 禁止事项

- 不伪造证据、不篡改引文、不把推断写成原文。
- 不把 B 级素材当 A 级硬约束。
- 不把“我不喜欢”写成“读者会不喜欢”。
- 不用“AI 味”当人格指控；给具体表达证据。
- 不泄露用户材料中的隐私/密钥。
- 不输出“已修改/已保存/已替换”的伪结果。
- 不在报告里塞完整对话 transcript；只给圆桌纪要。
- 不为了凑字数重复同一问题。
- 不把评分写成精确到小数点后两位的伪科学。

## 12. 交付格式

- 默认：直接在对话中输出 Markdown 报告。
- 用户要求保存：按 `.agents/skills/manuscript-review/runtime/READ_ONLY_AND_SAFETY.md` §6 新建文件，不覆盖。
- 长报告可分段输出，但必须一次给完整结构；不要只说“见附件”而不给内容。
- 报告开头给 3–5 行“对话摘要”，方便用户快速抓重点；摘要不替代完整报告。
- 用户明确要求“把讨论过程也给我”时，可附“圆桌纪要（扩展版）”：按轮次列关键发言/挑战/回应摘要。只写真实发生的发言，不伪造 transcript，不把主持的推断写成角色原话。

## 13. 自检清单（定稿前）

- [ ] 总分、等级、置信度、发布建议齐全且互相不矛盾？
- [ ] 故事设计分（Craft Index）与 10 项子分齐全、每项有证据、平均×2 算对？
- [ ] 是否说清“故事设计强于/弱于执行”，而不是只给总分？
- [ ] 每条 P0/P1 有位置、证据、机制、后果、改法？
- [ ] 引文逐字准确、锚点可定位？
- [ ] 严重度没有被情绪/角色投票抬高或压低？
- [ ] 维度分没有重复扣同一个问题？
- [ ] 加权与上限计算正确？
- [ ] A/B/C/D 素材级别用对了？
- [ ] 分歧与未决项没有被抹平？
- [ ] 亮点与“不要改”的部分写了吗？
- [ ] 只读声明与覆盖范围写了吗？
- [ ] 有没有越权替作者拍板 / 代写整章？
- [ ] 有没有“已修改文件”这类虚假声明？
