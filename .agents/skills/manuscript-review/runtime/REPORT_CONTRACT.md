# 报告契约（写作技巧优先）

> 报告是审核器唯一的产品。它必须让作者**看得懂、信得过、改得动**，而不是让评审团显得专业。
>
> **主评是写作技巧：好不好看、哪里不好看、怎么写更好。逻辑/设定一致性不是主评。**

## 1. 报告原则

1. **结论先行**：作者先看“好不好看”、总分、写作技巧分、最该改的三处，再看细节。
2. **证据可查**：每条问题带章/场/引文锚点；没有锚点的判断降为“观察”。
3. **可执行**：修改意见写到“删/移/补/换/压/放 + 技法”，不给“加强人物塑造”这类空话。
4. **给更好的写法**：至少 2–4 组“原文 → 可尝试的写法 → 技法”，短句示例，标注“不是代写”。
5. **有取舍**：明确“最该改”和“可以先不改”，避免把二十条问题平铺给作者。
6. **保留作者**：指出有效选择与亮点，说明哪些地方不要改坏；不把作品改成评审团的风格。
7. **不评逻辑/设定一致性**：本 skill 只评写作技巧；不审设定、时间线、知识边界。
8. **诚实**：材料不足、单位不足、意见分歧、无法判断，都要写出来；不制造确定感。

## 2. 语气与格式

- 默认用中文；用户明确要求英文/其它语言时切换。术语必要时给一句解释。
- 对作者说话，不用“本评审团认为”这类官僚腔；用“这场的问题在于……”“可以试试……”。
- 批评对事不对人：说“这场戏的转折缺少前置”，不说“作者不会写转折”。
- 不用打分羞辱（“不及格”“垃圾”）；等级是诊断标签，不是判决。
- 短句优先；每段不超过 5 行；问题清单用表格/列表。
- 引用正文用引号 + 锚点；引用不超过定位所需长度。
- 不剧透用户没提供的后续；如果用了后续材料，标注“含后续剧透”。

## 3. 报告结构（必须按顺序）

```markdown
# 正文审核报告：《<单位名/章名>》

## 0. 审核摘要
- 审核单位（第 X–Y 章 / 序列 / 幕 / 单章局部）与章节类型
- 总分 / 等级 / 置信度
- 写作技巧分（Craft Index）
- 好不好看（一句话）
- 最该先改的三处
- 发布建议（如用户需要）
- 只读声明

## 1. 审核范围与依据
- 素材状态（已提供/用户确认无/未确认）
- 审核对象（来源、字数、章数/场景数）
- 模式与轮次
- 上下文覆盖（前情/幕纲/人物卡/文风参考/后续）
- 能判什么/不能判什么
- 未纳入/缺失

## 2. 章节速写（单位地图）
- 一句话剧情
- 单位功能（这一幕/序列在卷/全书里做什么）
- 章节功能表（章/功能/POV/时间地点/关键事件/本章转折/对单位贡献）
- 贯穿线（求索/赌注/人物弧/关系/信息）
- 承诺/回收
- 幕末钩子

## 3. 分维度评价（写作技巧）
### 3.1 场景与戏剧效果
### 3.2 对白与人物声音
### 3.3 描写与文字
### 3.4 节奏与可读性
### 3.5 人物与情感
### 3.6 幕/序列效果
每节：分数 + 一句理由 + 2–5 条关键 findings + 一条“有效/可保留”
### 3.7 写作技巧评分（Craft Scorecard 10 项，1–5）
### 3.8 幕/序列结构诊断（可选，幕/序列模式填）

## 4. 关键问题清单
| ID | 严重度 | 类型 | 位置 | 问题（写作技巧） | 读者影响 | 改法方向 |
（P0 在前，P1 次之，P2 最后；OBS 单列）

## 5. 修改方案（按优先级）
### 5.1 更好的写法（原文 → 可尝试 → 技法；2–4 组）
### P0 · 必须处理
### P1 · 建议处理
### P2 · 打磨项
### 不建议改的地方

## 6. 圆桌争议与未决问题
## 7. 亮点与保留项
## 8. 评分明细
## 9. 覆盖范围、限制与只读声明
## 附录 A. 证据锚点索引（可选）
```

## 4. 长度建议

| 模式 | 正文字数（不含引用） | 说明 |
|---|---|---|
| quick | 800–1,500 字 | 3–5 条关键问题，不铺开 |
| standard | 2,000–4,000 字 | 完整六维 + P0/P1/P2 + 更好的写法 |
| deep | 4,000–8,000 字 | 增加逐章/逐场分析、争议记录、证据索引 |

长度不是硬指标。宁可 2,500 字说清楚，也不要 8,000 字重复同一件事。

## 5. 问题条目写法

每条必须包含五件事：

1. **位置**：章/场 + 引文；
2. **问题**：具体是什么，不贴空泛标签；
3. **为什么**：写作机制（场景目标、视角、节奏、信息交付、人物欲望……）；
4. **读者影响**：读者会怎样（出戏、疲劳、看不懂、不想追）；
5. **怎么改**：动作 + 技法 + 可选示例 + 代价。

合格示例：

> **P1 · 场景 · 第 3 章·第 2 场**
> 位置：`[第3章·场景2·"他把信折好，放进抽屉最底层"]`
> 问题：林砚决定隐瞒信件，但前文没有“他为什么不信任沈鸢”的铺垫。
> 为什么：读者只知道两人是盟友，缺少“隐瞒”的动机；这个动作更像作者需要信息延后，而不是人物选择。
> 读者影响：读者会觉得人物突然变得防备，后面“沈鸢发现信件”的冲突会像硬拗。
> 改法：① 在第 2 章加一个沈鸢替林砚做决定、越过他边界的细节，让“不信任”有具体来源；② 或把隐瞒改成“他想说但被打断”，保留信息延后，同时不伤害关系逻辑。
> 技法：**把解释改成动作/前史细节**；示例（不是代写）：沈鸢替他答应了差事，他看了她一眼，把话咽回去。代价：第 2 章会多 100–200 字。

不合格示例：

> 人物不够立体，建议加强人物塑造。
> 节奏有点慢，建议加快。
> 设定有问题，建议完善世界观。

不合格原因：没有位置、没有机制、没有可执行动作、无法验证。

## 6. 严重度定义（写作技巧）

| 级别 | 定义 | 判断标准 | 处理建议 |
|---|---|---|---|
| **P0 · 阻断** | 不修会让这一章/这一幕“读不下去/不想看” | 场景无功能；叙述不可读；主角完全无欲望/无行动；幕级逆转缺失；核心体验失效 | 必须处理，优先于文采 |
| **P1 · 重要** | 明显影响阅读体验/情绪/节奏，但章节仍成立 | 场景转折弱；对白无行动；描写套话/无 POV；节奏失衡；人物动机不足；章末无钩 | 建议处理，可分批 |
| **P2 · 打磨** | 局部优化，不影响理解 | 语言重复；句式单调；比喻不准；段落节奏；标签过多 | 有余力再改 |
| **OBS · 观察** | 可能是风格/类型选择，证据不足以判错 | 作者可能有意为之；取决于后续；类型惯例 | 只提示，不要求改 |

**P0 是写作技巧阻断，不是“设定冲突”。** 本 skill 不评设定/逻辑一致性。

## 7. 修改方案写法

### 7.1 动作词表

- **删**：删掉某句/某段/某场，说明删后损失什么、如何补。
- **移**：把信息/场景/揭示移到更合适的位置，说明为什么。
- **补**：补一个动作、细节、过渡、动机桥，说明补多少、补在哪。
- **换**：换视角/换表达/换冲突方式，说明替代方案。
- **压**：压缩解释/重复/描写，说明压到多少。
- **放**：放慢/展开关键 beat，说明展开什么。

### 7.2 技法标签

修改方案尽量带一个技法标签，让作者能复用：

- 解释→动作/物件；情绪→身体/选择；全知→POV 过滤；信息倾倒→冲突中交付；
- 对白直给→答非所问/潜台词；声音雷同→词汇/句长/遮掩方式；
- 场景无转折→价值翻转；动作堆砌→选择/代价；套话→具体细节；
- 比喻过多→一个准确比喻；总结句→删掉让动作说话；章末平收→具体期待；
- 人物无欲望→具体目标；反派工具人→自己的账本；入口太慢→从异常/冲突开始；
- 出口拖尾→在决定点结束；高潮被解释→用选择/代价收。

### 7.3 示例的边界

- 可以给 1–2 句示例，帮助作者理解动作；必须标注“示例，不是代写”。
- 不给整段/整场重写，除非用户明确要求“示范改写”；即使如此，也只给局部，并说明这不是唯一解。
- 示例要贴合作者现有文风，不要趁机展示评审团的文采。

## 8. 当问题很少 / 没有问题

- 不要为了显得认真而硬凑问题。可以写“本次未发现 P0/P1；以下为可选打磨项”。
- 如果确实优秀，明确说优秀在哪，给高分；不要用“但是”稀释。
- 如果只发现 1–2 个小问题，报告可以短；不必凑满六维长文。
- “没有发现问题”不等于“没有审”：要说明审了什么、覆盖到什么程度。

## 9. 当材料不足

- **素材状态未确认**：写“用户未提供设定/人物卡，且未确认是否存在；以下判断仅按文本内写作技巧，置信度低”。**不要写“无素材”**。
- **缺失前情/幕纲**：写“缺前情/幕纲，人物状态/幕功能判断受限，置信度中/低”。
- **缺失人物卡/文风参考**：写“人物声音/作者声音判断只能按文本内自洽”。
- **单章局部诊断**：写“只评本章写作技巧，不判断幕逆转/人物弧/求索/伏笔回收”。

本 skill **不评设定/逻辑一致性**；不要因为“设定冲突”降总分。

## 10. 只读声明（必须出现）

报告末尾固定包含：

```text
只读声明：本次审核仅读取上述材料，未对任何用户提供的输入文件执行写入、重命名、移动或删除。
报告直接输出在对话中。/ 报告已新建于：<路径>（用户明确要求保存）。
```

如果运行中出现异常（子代理失败、材料读取失败、权限不足），在声明前加“运行异常”小节，不要隐瞒。

## 11. 禁止事项

- 不伪造证据、不篡改引文、不把推断写成原文。
- 不把“我不喜欢”写成“读者会不喜欢”。
- 不用“AI 味”当人格指控；给具体表达证据。
- 不泄露用户材料中的隐私/密钥。
- 不输出“已修改/已保存/已替换”的伪结果。
- 不在报告里塞完整对话 transcript；只给圆桌纪要。
- 不为了凑字数重复同一问题。
- 不把评分写成精确到小数点后两位的伪科学。

## 12. 交付格式

- 默认：直接在对话中输出 Markdown 报告。
- 用户要求保存：按 `runtime/READ_ONLY_AND_SAFETY.md` §6 新建文件，不覆盖。
- 长报告可分段输出，但必须一次给完整结构；不要只说“见附件”而不给内容。
- 报告开头给 3–5 行“对话摘要”，方便用户快速抓重点；摘要不替代完整报告。
- 用户明确要求“把讨论过程也给我”时，可附“圆桌纪要（扩展版）”：按轮次列关键发言/挑战/回应摘要。只写真实发生的发言，不伪造 transcript。

## 13. 自检清单（定稿前）

- [ ] 单章局部诊断有没有冒充“幕级总分”？
- [ ] 每条 P0/P1 有位置、证据、写作机制、读者影响、改法？
- [ ] 有没有 2–4 组“原文 → 可尝试 → 技法”的具体示例？
- [ ] 引文逐字准确、锚点可定位？
- [ ] 严重度没有被情绪/角色投票抬高或压低？
- [ ] 维度分没有重复扣同一个问题？
- [ ] 加权与 P0 上限计算正确？
- [ ] 写作技巧分（Craft Index）与总分的关系解释了吗？
- [ ] 分歧与未决项没有被抹平？
- [ ] 亮点与“不要改”的部分写了吗？
- [ ] 只读声明与覆盖范围写了吗？
- [ ] 有没有越权替作者拍板 / 代写整章？
- [ ] 有没有“已修改文件”这类虚假声明？
- [ ] 有没有混入设定/逻辑一致性审判？本 skill 不应有。
