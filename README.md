# 正文审核器（Manuscript Review）

> 给一章正文和一堆零散素材，让七个专业角色真的吵几轮，最后只交一份能落地的审核报告。
>
> **只读。不改稿。不碰你的文件。**
>
> 当前版本：`0.1.2`（beta）｜OpenCode / Claude Code / Codex 三端适配

## 这是什么

正文审核器是一个面向**已有正文**的多角色审核 skill。它不写小说，不做设定，不生成大纲。它只做一件事：

> **评价这一章写得怎么样、问题在哪、该怎么改。**

用户通常会给：

- 一章/一段/多章正文（必需）；
- 任意素材：世界观、人物卡、关系表、大纲、前文、后续剧透、文风样本、参考作品、读者评论、平台要求……（可选，类型不限，可能互相矛盾，也可能根本没有）。

审核器会先把材料分级（哪些是硬设定、哪些只是参考、哪些已过期），再让不同专业角色独立审、互相质询、由魔鬼批评挑错，最后收敛成一份报告。

## 为什么不是“一个模型写一篇读后感”

因为单模型审稿有三个常见毛病：

1. **什么都夸/什么都骂**：没有稳定标准；
2. **证据不足**：说“人物崩了”，但指不出哪一句、为什么；
3. **越改越像评审团**：把作者的个人风格当成错误铲平。

这个项目用七个角色分工 + 多轮对抗 + 证据锚点 + 只读边界来解决：

- 世界观、人物、结构、场景各管一段，不越权；
- 拆解员负责“原文到底写没写”，让评审团不能凭空说话；
- 魔鬼批评负责“你们是不是骂错了/夸错了”，但必须先钢人化；
- 秘书只整合，不新增判断，不抹平分歧；
- 主持负责最终裁定与报告。

## 七个角色

| 角色 | Stable ID | 管什么 | 不管什么 |
|---|---|---|---|
| 世界观与设定 | `worldbuilding` | 规则、制度、资源、信息传播、设定一致性 | 人物动机、结构、对白 |
| 人物与关系 | `character` | 动机、选择、OOC、知识边界、关系连续、声音 | 世界规则、场景写法 |
| 结构与节奏 | `story_plot_structure` | 章节功能、因果、升级、赌注、承诺、节奏、结尾 | 人物心理、对白 |
| 场景与对白 | `scene_dialogue` | 场景目标、beat、对白行动、潜台词、信息交付、语言 | 人物动机、世界规则、结构 |
| 文本拆解与核证 | `story_deconstructor` | 章节地图、事实台账、时间线、承诺表、素材覆盖、引文核证 | 评好坏、裁严重度 |
| 魔鬼批评 | `devil_critical_review` | 钢人化、隐藏假设、反例、失败路径、误报、虚高、副作用 | 接管专业裁决 |
| 审核秘书 | `secretary` | 报告整合、证据/算术/分歧检查 | 新增判断、改裁定 |

主持（Chairman）由主线程担任，不单设子代理。

## 快速开始

### OpenCode

打开本仓库根目录，然后：

```text
用正文审核器审一下第 17 章。
正文：/path/to/ch17.md
素材：
- /path/to/人物卡.md（必须遵守）
- /path/to/旧大纲.md（仅参考，可能过期）
目标：判断能不能发，并给修改意见。
```

也可以显式点名 skill：`manuscript-review`。

### Claude Code

打开本仓库根目录。Claude Code 会从 `.claude/skills/manuscript-review/` 发现入口，从 `.claude/agents/` 发现七个子代理。用法同上。

### Codex

打开本仓库根目录。canonical skill 在 `.agents/skills/`，子代理在 `.codex/agents/`。用法同上。

### 安装到已有小说项目

本仓库可以直接作为独立项目打开；也可以把 skill 移植到已有的小说文件夹：

1. 复制 `.agents/skills/manuscript-review/` 到目标项目的同一路径；
2. 复制你所用宿主的适配层：
   - OpenCode：`.opencode/agents/*.md`
   - Claude Code：`.claude/agents/*.md` + `.claude/skills/manuscript-review/`
   - Codex：`.codex/agents/*.toml`
3. 重开项目/会话，让宿主重新发现 skill 与子代理；
4. **不要盲目覆盖**目标项目已有的 `AGENTS.md` / `CLAUDE.md`；把本项目的“只读审核”规则合并进去；
5. 若目标项目已有同名 agent（例如 `character`），先确认是否会冲突；必要时改成 `review_character` 等名字，并同步修改 skill 里的 Stable ID 映射。

### 最小输入

只有正文和“帮我审一下”也能跑，**但审核器会先问一次素材**：

> 这章有没有设定、人物卡、大纲、前文、文风参考？可以给我文件或文件夹路径；如果没有，回复“没有”，我就按纯文本内自洽模式审。

- 你说“没有” / “只看正文” → 进入纯文本模式，报告写明“用户确认无外部素材，设定一致性判断受限”。
- 你给文件或文件夹 → 先列清单、确认纳入范围，再按 A/B/C/D 分级分析。
- 你只回“嗯 / 继续 / 你看着办” → 审核器会再确认一次，不会把“没给”当成“没有”。

这样不会出现“用户其实有设定，但审核器直接按没设定开审”的漏判。

## 三种深度

| 模式 | 什么时候用 | 发生什么 |
|---|---|---|
| `quick` | 短片段、只想快速看 | 独立审 + 轻量收敛，3–5 条关键问题 |
| `standard`（默认） | 大多数章节 | 独立审 → 交叉质询 → 收敛；两轮讨论 |
| `deep` | 卷末、高潮、关键转折、争议大的稿 | 再加一轮复核与魔鬼终检；逐场分析 |

用户说“快速看看”/“深度审”会自动切换；没说就 standard。

## 报告里有什么

1. **审核摘要**：总分、等级、置信度、一句话判断、最该先改的三处、发布建议。
2. **审核范围与依据**：读了什么、素材 A/B/C/D 分级、能判什么/不能判什么。
3. **章节速写**：场景表、时间线、信息揭示、承诺与回收——事实层，不评好坏。
4. **分维度评价**：人物与矛盾、故事设计与结构、场景执行与对白、设定、语言，各给分数 + 理由。
5. **故事设计评分（Craft Scorecard）**：激励事件、求索、鸿沟、场景价值转折、幕/序列逆转、不归点、危机/高潮、人物矛盾、人物弧、类型契约，10 项各 1–5 分，另给“故事设计分（Craft Index）”。
6. **P0/P1/P2 问题清单**：每条带位置、证据、后果、修改方向。
7. **修改方案**：按优先级，具体到删/移/补/换/压/放，含可选短示例与代价。
8. **素材一致性核对**：A 级冲突单列；B/C 级只作建议；D 级列冲突。
9. **圆桌争议**：谁和谁没谈拢、主持怎么裁、还缺什么。
10. **亮点与保留项**：哪些地方不要改坏。
11. **评分明细 + 覆盖范围 + 只读声明**。

示例结构见 `.agents/skills/manuscript-review/templates/REPORT_TEMPLATE.md`。

## 评分怎么算

**五个维度**，默认权重：

```text
人物与矛盾 25% + 故事设计与结构 25% + 场景执行与对白 25% + 设定与世界逻辑 15% + 语言与阅读体验 10%
```

- 1–10 分，0.5 刻度；
- P0 会触发总分上限（1 条 ≤ 6.5，2 条 ≤ 5.8，3 条以上 ≤ 5.0；核心功能/因果断裂 ≤ 5.0），**只压不抬**；
- 置信度低时给区间分，不装作精确；
- 分数必须能由 findings 支撑，不能先定分再找理由。

**故事设计分（Craft Index）**回答“是否好看”，与总分并列：

```text
激励事件 / 求索 / 鸿沟 / 场景价值转折 / 幕·序列逆转 / 不归点 / 危机·高潮 / 人物矛盾 / 人物弧 / 类型契约
→ 10 项各 1–5 分 → 平均 × 2 = 故事设计分（1–10）
```

- 它不加权进总分，避免与人物/结构/场景重复计分；
- 故事设计分明显低于总分 → 逻辑/文字尚可，但故事设计是短板；
- 故事设计分明显高于总分 → 故事有想法，但执行/逻辑/文字拖后腿。

详细规则：`.agents/skills/manuscript-review/runtime/SCORING_RUBRIC.md`；透镜问题与强弱信号：`.agents/skills/manuscript-review/runtime/STORY_CRAFT_LENS.md`。

## 只读保证

- 不修改、不重命名、不移动、不删除、不创建用户文件；
- 不执行写入型命令、不跑脚本、不做 git 写操作；
- 报告默认只输出在对话里，不在磁盘上生成；
- 用户明确要求“保存报告”时，只在指定路径新建一个报告文件，不覆盖已有文件；
- 用户要求“直接帮我改”时，拒绝写入，改为给修改方案。

准确表述是：**本次运行未调用任何写入操作**。详见 `.agents/skills/manuscript-review/runtime/READ_ONLY_AND_SAFETY.md`。

## 素材分级（关键设计）

| 级别 | 是什么 | 能用来干什么 |
|---|---|---|
| **A 硬约束** | 用户明确说“必须遵守/以这个为准”的设定、人物卡、大纲 | 判“设定冲突”（P0 候选） |
| **B 参考** | 旧稿、灵感、参考作品、未确认脑洞 | 提供修改灵感，不单独判错 |
| **C 目标** | 平台、读者、字数、类型期待 | 调整评价标准与建议优先级 |
| **D 冲突/存疑** | 多版本矛盾、来源不明、过期 | 标冲突，不静默择一 |

**素材的沉默不是禁止。** A 级没写“主角不会飞”，不等于主角飞了就是错。只有当 A 级明确规则、正文违反时，才是硬冲突。

## 自定义

- **改角色关注点**：编辑 `.agents/skills/manuscript-review/roles/<id>.md`。角色契约是唯一权威，宿主适配层不需要同步改。
- **改检查清单**：编辑 `.agents/skills/manuscript-review/runtime/REVIEW_CHECKLISTS.md`。
- **改权重/上限**：编辑 `.agents/skills/manuscript-review/runtime/SCORING_RUBRIC.md`，但要在报告里披露调整。
- **加类型契约**（网文/悬疑/言情等）：在 `.agents/skills/manuscript-review/runtime/REVIEW_CHECKLISTS.md` §6 扩展。
- **加宿主**：在对应目录加薄适配器，指向同一个 `.agents/skills/manuscript-review/roles/<id>.md`，不要复制出第二套逻辑。

## 开发自检

本仓库自带只读的结构测试与报告检查，不会修改用户文件：

```bash
python3 -m unittest discover -s tests -v
python3 .agents/skills/manuscript-review/scripts/check_report.py examples/sample_report.md
```

`check_report.py` 用于检查一份**已经保存**的报告是否包含必需章节、只读声明、评分范围、P0 证据锚点与未替换占位符。它是离线工具，不属于审核运行时。

## 已知边界

- 它评的是**这一章当前的样子**，不是作者的潜力、市场表现或文学史地位。
- 没有前文/大纲时，跨章因果、伏笔回收、人物弧只能给条件判断。
- 素材冲突时，它会把选择权交回作者，而不是替作者拍板。
- 评分是诊断工具，不是终审判决；不同评审标准下分数会变。
- 它不会为了显得专业而硬凑问题；问题少时报告会短。
- 它不代写。示例最多 1–2 句，且明确标注“不是代写”。

## 设计来源

角色分工、证据优先、只读边界、越权纪律、钢人化后再攻击、秘书不新增判断等治理思路，来自早期的 **Novel Council** 项目。本项目把这些专业角色从“创作/Story Bible”场景中抽出来，重组为**已有正文的审核流程**，不再承担 Canon、规划、设定生成等职责。
